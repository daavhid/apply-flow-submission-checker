Q&A diagnostics: failed batches and failed whole requests expose an expandable Q&A error-details panel. It retains up to ten unique failures in sidebar memory and supports Copy error details/Clear details. The allowlisted report includes parent/batch request IDs, generation/polling/context stage, transport HTTP status, reported or inferred provider status, backend code, safe endpoint path and reported provider run ID. HTTP 200 status polling may still report a failed provider job (for example provider 429/quota exhaustion). Guidance distinguishes quota, authorization, timeout, cancellation and context changes. Raw request/response bodies, resume text, question/answer content, credentials and URL query strings are excluded from the copy report. Provider/model/run fields are available only when the backend reports them.

Deployed PDF delivery: settings.json resume.applyFlowFormat defaults to pdf (original preserves server format when explicitly configured). Application-context requests include preferredResumeFormat=pdf while allowResumeGeneration remains false. ApplyFlow should return the existing PDF in resume.file with filename, mimeType=application/pdf, same-origin url and its own sha256. Explicit variants under resume.pdfFile, resume.files (array or map) or resume.file.variants can also provide PDF metadata for this verified resume/candidate/job. A DOCX-only response cannot be silently attached under PDF policy. Missing PDF blocks automatic file attachment, not the already parsed text used for question context. Never rename DOCX bytes to .pdf or reconstruct an attachment from parsed text.

Skill normalization: arrays of skill strings or structured entries using name/skillName/skill/label/technology/title/value are normalized to actual unique names. Nested skill collections are read without rendering object strings. Unsupported metadata is ignored rather than stringified. If facts omit workHistory, parsed resume records remain available.

Answer review lifetime: progress-only jobVersion updates no longer discard an already validated answer batch in the sidebar or invalidate an unchanged DOM question binding. Application/candidate/profile/assignment/selected-resume versions remain bound, and visible job title/company changes invalidate the review. The backend screening request/response jobVersion and post-generation checks remain strict; this change does not bypass a provider/API VERSION_MISMATCH. The backend should provide a stable content version separately from progress timestamps to prevent spurious provider-version conflicts.

Shared ZIP connection default: config/connection.js embeds https://applyflow-api.jhproit.com. A clean install initializes that saved endpoint in signed-out state and goes directly to email/password sign-in; there is no required API URL setup step. No credentials or provider secrets are bundled. An explicitly saved workspace remains selected for existing installations. Original endpoint selection cannot come from a job URL. Rebuild the ZIP after changing the release default.

A 409 with those IDs present is a backend rejection, not proof that the extension discarded tracking. Older updates may already have deleted IDs; open the original tracked link once if no recovery record exists.

1. Candidate reference facts are NOT job resumes. profile.baseContextText (or
profile.baseContext) may hold a reference document with Candidate Information.
SQC extracts explicitly labeled contact/location, official employer/title/date
rows and education/graduation facts from that section. Structured profile fields
win. Missing streets, authorization and technology experience are never inferred.
Generator instructions, examples, keyword lists and fictional-project prompts are
excluded. Raw reference text is not an attachment or AI resumeContext. If a base
resume response accidentally contains a generator prompt, its reference facts are
retained but resume becomes null; no original is downloaded from that object.
Supply the actual generated job document separately as resume.kind:tailored with
jobId, verified profileId, parsed document text and original file metadata/bytes.

2. Multiple assigned profiles are verified per tab. assignedProfiles entries must
include the validated assignment/profile pairs documented below. Launch profile
IDs resolve against that roster; the matching assignment is used without changing
the account's default profile or another tab. Candidate name is shown while
verification is pending when it is known from the roster, and on every workspace
tab after verification. When a launch omits profileId, the backend's returned
profile must still belong to the verified roster and match the application ID.

3. Resume flow has three distinct states: candidate facts, selected original job
resume, and the file actually attached to the portal. A user upload takes priority
over ApplyFlow's existing tailored file for that application. Hidden native file
inputs behind visible Attach buttons are supported, scoped to Resume/CV rather
than Cover letter or inactive forms. An existing portal attachment can be imported
explicitly with Use attached resume as context. After parsing and candidate/job
validation, SQC normalizes the portal filename only when its bytes equal the
selected original. Different files are never silently replaced. Parsed text is
for facts/answers only and is never rebuilt into a PDF or attachment.

4. Availability is checked from visible main-page content and browser-observed
main-document HTTP responses. A stable 404/410, soft-404 or explicit job-closed
notice is confirmed twice at least 1.2 seconds apart before a terminal report.
Hidden notices, footer text, login/CAPTCHA, HTTP 401/403/429, network/5xx failures,
expired metadata alone, and conflicting active forms do not prove a closed job.
Confirmed unavailable pages pause autofill, AI, resume prompts and attachments.
SQC sends PORTAL_ACCESS_FAILED, is_final_submission:false,
submission_confirmed_by:AUTO_DETECTED_JOB_UNAVAILABLE and portal_evidence with
type:JOB_UNAVAILABLE_NOTICE, exact URL, visible evidence, observedAt and optional
httpStatus. ApplyFlow maps this to LINK_NOT_FOUND, acknowledges the event, and must
never downgrade an APPLIED record. SQC also protects known applied records locally.
See Chrome's network observation API: https://developer.chrome.com/docs/extensions/reference/api/webRequest

5. Live progress remains non-final. Empty controls, placeholders, default profile
metadata and credentials do not start progress telemetry. Actual input or a
resume attachment sends validation_status:IN_PROGRESS to live-event after a quiet
500ms, no faster than once per 1.5 seconds. Duplicate snapshots are skipped. The
correlated IN_PROGRESS acknowledgement is displayed as live progress, never as
completion. Submission still requires portal evidence and its final acknowledgement.

6. Background detection is passive while an applier edits. Unchanged native
selects do not dispatch change/input events; unsupported custom labels are not
rewritten. Autofill pauses for focused controls/open dropdowns. Failed AI fills
remain for review rather than repeating until accepted. Manual Fill answer and
Fill ready answers remain available after the applier finishes editing.

may report APPLIED or SUBMITTED: both represent completion in the sidebar.

AUTHENTICATION IS ACCOUNT SYNC ONLY (1.4.1)
SQC login and password changes return only authenticated applier/assignment
context; they do not resolve a job, fetch a file or generate a resume, even if a
caller supplies tabId. POST /api/sqc/login includes allowResumeGeneration:false.
GET /api/sqc/session and all authentication routes MUST be free of resume
generation, tailoring, application creation and submission side effects.

POST /api/sqc/application-context now includes resumePolicy:"existing-only" and
allowResumeGeneration:false. Return an existing approved resume or resume:null.
Never generate or regenerate a document while verifying status or reading context.
GET resume.file.url must retrieve an existing file without triggering generation.
When no suitable file exists, SQC requests an upload. Generating/tailoring a new
resume is a separate explicit ApplyFlow workflow, never an authentication action.

Only an authoritative /api/sqc/session rejection signs out the account. A job
request returning 401 pauses that job; a resume download returning 401 reports a
file-access error. Neither response alone proves the user is signed out. A
temporary session network/5xx failure may display the last synced account in the
sidebar, with actions paused and accountVerified:false; it never grants a lease.
Confirmed session rejection clears identity and remains signed out until login.
If login succeeds but /session immediately returns 401, verify that its HttpOnly
session cookie is retained for extension credentialed fetches (including the
existing SameSite/Secure, CORS and CSRF requirements). Do not return success before
the authenticated session is available. Do not couple session refresh to document
generation or return HTML/website-login redirects to the extension.

GUIDED SIDEBAR WORKSPACE (1.4)
The toolbar opens a sidebar with inline workspace URL, email/password and required
password-change forms. After login, Overview shows the authenticated account and
assigned candidate profiles even when no job is open or a portal route is denied.

to override the active lock. A plain list of candidate names is not assignment
proof. The backend must still provide the active assignment for job verification.
Missing assignment data is shown explicitly rather than as a missing job context.

UNIFIED SIDEBAR AND COMPLETION EVIDENCE (1.2)
The main release uses one Chrome sidebar for SQC status, resume handling and Q&A.
It is bound to the active tab and authenticated assignment. The uploaded original
passes through SQC_SET_LOCAL_RESUME, with candidate-header validation and per-job
storage; it cannot change the assigned candidate. AI uses the configured ApplyFlow
origin with the current session cookie and CSRF header. The standalone Q&A release
remains separate and does not use this managed-assignment adapter.

SQC retains sqcTabBindings (applicationSessionId, jobId, profileId, auth session and
assignment versions) per tab in trusted session storage. Unapproved continuation
URLs send these IDs and previousApplicationSessionId as lookup hints. They NEVER
authorize identity: the backend must revalidate the application, assignment and
versions. allowedRoutes is optional in 1.5. Backend-denied responses remove the usable lease
but retain lookup hints. Sign-out/reassignment invalidates them; closing a tab
removes its binding. Explicit launches for another job establish a new binding.

A valid form, submit click, wizard Next button or generic Confirmation URL/title
is not completion evidence. Completion requests include is_final_submission:true,
submission_confirmed_by:CONFIRMED_ON_PORTAL_SUCCESS_PAGE (or the existing
AUTO_DETECTED_ALREADY_APPLIED_ON_PORTAL), and portal_evidence with type
SUCCESS_NOTICE or ALREADY_APPLIED_NOTICE, visible message, exact source URL,
observedAt ISO timestamp and intermediate:false. SQC rejects missing, manual,
intermediate, foreign-page and stale evidence. Content checks visible portal
evidence again after screenshots. Backend ownership/version validation and an
accepted acknowledgement with matching event/session IDs and nonempty recordId
are still required before local completion is displayed. Enforce these checks on
the server as well; browser evidence does not replace server authorization.

ApplyFlow integration contract for SQC

Implement this contract in the ApplyFlow backend to enable the SQC authentication,
candidate profile, job context, and audit synchronization already implemented in
this repository. Contract version: 2. These new authentication/context routes are
requirements for the ApplyFlow agent; their existence is not assumed.

Scope

SQC now uses one user-selected ApplyFlow API origin. The user signs in with their
ApplyFlow applier email and password. The authenticated server session returns
the candidate profile assigned to that applier, which is locked across SQC job
tabs. Each job context must match this profile lock. Profiles are no longer seeded from JSON.
Candidate editing, local reassignment, admin passkeys, and extra webhook targets
are disabled. The existing ChatGPT copy/paste tools remain available only inside
a verified assignment. Screening requests are integrated with ApplyFlow; the
general chat UI is separate from application answering.

Authentication transport

The endpoint is the ONLY integration setting the installer/user supplies. Do not
ask the user to enter candidate IDs, applier IDs, API keys, extension IDs, AI
provider settings, or separate webhook URLs. The applier supplies their assigned
email and password in the dedicated SQC setup page. SQC sends
credentials to the configured ApplyFlow server and never stores them. ApplyFlow
owns account creation, credential verification, password policy, and assignments.
The extension opens its centered setup page on first installation, persists
the endpoint across browser restarts/extension updates, and uses the same flow
for an unpacked local installation and a Chrome Web Store installation.

1. The user enters the API origin in onboarding/onboarding.html and continues.
   HTTPS is required, except HTTP on localhost/127.0.0.1/[::1]. Paths, credentials,
   query strings, and hashes are rejected. Portal URLs cannot select API origins.
2. SQC checks GET /api/sqc/auth before accepting a new server, then requires
   explicit email/password sign-in through POST /api/sqc/login. It does not open
   a website login or adopt an existing website session during initial setup.
   ApplyFlow may be open in another Chrome profile or browser. No website login
   is required in the browser profile where the extension is installed.
3. All API calls originate in the service worker, use credentials: include,
   cache: no-store, and reject redirects. The login POST must establish the API
   session cookie in the extension's browser profile; subsequent API calls use
   that session. If ApplyFlow currently accepts only bearer tokens,
   add a supported cookie-based adapter for these routes before enabling SQC.
4. Permit the deployed chrome-extension://<extension-id> origin and the
   Content-Type, X-SQC-CSRF, and X-SQC-Extension-Id request headers. SQC supplies
   its actual chrome.runtime.id automatically on every request, for both unpacked
   and Store builds. Do not ask the user for this ID. Register permitted Store
   and development extension origins centrally on the backend. The extension ID
   is public client metadata, never proof of identity or assignment authorization.
   Configure credentialed responses
   for this origin explicitly; do not combine credentialed access with '*'.
   Test the actual Chrome cookie policy in the target deployment.
   In particular, test credential sign-in in a fresh browser profile with no
   ApplyFlow website cookies; a website session in another profile is irrelevant.
5. GET /api/sqc/session returns a session-bound CSRF token. The login POST uses
   the separate pre-authentication token from GET /api/sqc/auth. All POST requests
   include X-SQC-CSRF. Validate it, session access, and assignment ownership on
   the backend. No bearer token or CSRF token is exposed to portal content scripts.
6. 401 means signed out/expired; 403 means access denied/revoked. Never redirect
   API requests to login HTML. Return JSON errors for all other non-success cases:
   {"success":false,"error":{"code":"CONTEXT_MISMATCH","message":"..."}}

Extension setup and ready state

The setup page shows one step at a time: server, credentials, assigned profile
review, then the ready workspace. A temporary password must be changed before
profile review. Accounts without a candidate remain on an assignment waiting
screen with a retry action. Profiles are supplied by the server, never selected
or edited locally. Reviewing a profile records only a UI acknowledgement keyed
to the server, applier, assignment, and profile versions. It grants no permission
to autofill or submit; every portal still requires a backend-verified job context.

After setup, the toolbar popup shows the HUD-style workspace and waits for an
application. A verified active job tab shows its title and company. The portal
HUD sends unauthenticated users to the dedicated setup tab using OPEN_SETUP;
the service worker focuses an existing setup tab instead of opening duplicates.

Provision the applier account and initial email/password in ApplyFlow using the
existing authorized administration flow. SQC does not create users or carry a
shared default password. A temporary password can be marked passwordChangeRequired

Headers: Content-Type:application/json; X-SQC-CSRF:<pre-authentication token>

POST /api/sqc/password
Headers: Content-Type:application/json; X-SQC-CSRF:<authenticated session token>
Body: {"currentPassword":"user_current_password","newPassword":"user_new_password"}
Response: {"success":true,"contractVersion":2}

Verify the current password, enforce the existing backend password policy, change

Headers: Content-Type:application/json; X-SQC-CSRF:<authenticated session token>

Response: {"success":true,"contractVersion":2}

must not silently reuse a leftover cookie. Sign-in explicitly clears this local
lock only after credential verification. Disconnecting the endpoint is separate
from signing out; use Sign out to revoke the authenticated session.

Tailored resume uploads and source of truth

Each application uses either an uploaded tailored resume or an approved
ApplyFlow resume with kind:tailored and a matching jobId. Upload through
HUD > Resume > Upload tailored resume > Use tailored resume. The save button
confirms candidate/job ownership; there is no additional confirmation checkbox.
PDF, DOCX, and TXT files up to 10 MB are supported. SQC extracts readable text, displays experience
rows for review, and requires confirmation of the candidate/job. If extraction
fails, the applier can paste readable text alongside the original file.

ApplyFlow remains the source of truth for the base candidate profile: identity,
contact information, work authorization, sponsorship, location, compensation,
demographics, and other approved profile facts. Return these as structured,
versioned fields in session.profile and context.profile. A server-provided
verification prompt can accompany them as profile.verificationPrompt, but must
not be the sole representation of verification facts. SQC must not reconstruct
identity or legal eligibility from resume prose or from an AI answer.

The uploaded resume is a separate, applier-provided source for work-history
entries, descriptions, skills, and explicitly stated experience numbers. It
never updates the candidate's base profile. SQC labels it source:sqc_upload,
verified:false, and assigns resumeId 'sqc-upload:<file SHA-256>' and resumeVersion
'<file SHA-256>'. Those IDs are local document identifiers, not ApplyFlow resume
records. Original bytes are retained in extension-owned IndexedDB with a browser
session epoch and bounded retention, scoped to the authenticated account,
assignment/profile/job versions and application session. A local upload does
not depend on ApplyFlow's default resume ID/version; refreshing that default
does not discard the selected upload. A byte-matched downloaded ApplyFlow copy
is persisted with server provenance and is invalidated if its server version or
fingerprint changes. Logout clears the local documents. Assignment/job/version changes
invalidate them; the document must be uploaded for the new application context.

A valid job/profile assignment can return context.resume:null when no server
resume exists. This verifies the assignment, not a nonexistent resume. Basic
candidate details remain fillable, while resume-driven answering waits for an
upload. Existing approved server resume metadata/downloads remain supported for
viewing and attachment. A verified job-tailored server resume is ready without
re-upload. An unclassified/base document does not satisfy job tailoring.

Parsed employment rows retain exact source evidence, company, role, month/year
dates, current-employment status, and responsibilities. Supported existing
experience rows are filled in order. The extension does not create arbitrary
portal-specific rows or invent missing employers, dates, or durations. The user
must review parsed rows, add missing portal rows, and complete unsupported
controls. A month-only source never produces an invented day. Explicit numeric
experience facts include their source sentence; unknown skill durations are
left for review. Ambiguous dates and employment layouts remain unfilled.

Manual Q&A workflow

The HUD Questions button opens a manual-only Q&A tab. SQC does not collect form
questions for this tab, send batches on page load, or autofill returned answers.
The applier pastes only the questions they want answered (one per line), then
clicks Send pasted questions to ApplyFlow. Returned answers stay visible in
editable cards with Copy answer controls. Sending another request preserves
previous answers until the assignment or resume changes. Stop cancels a pending
request. Candidate/profile autofill and resume experience autofill remain separate
from Q&A; enabling them must never trigger a question-generation request.

Check AI connection explicitly GETs /api/ai/status (or /api/ai/health on a 404/405)
without sending questions. It displays the provider/model and what the backend
reports about readiness. A reachable discovery route is not proof that generation
works. The SQC answer route is preferred; if it is missing (404/405), SQC tries
/api/submissions/answer-questions, then /api/ai/answer-questions on the same saved
origin, with the same authentication, CSRF, payload, and response requirements.
Provider/model errors, authentication failures, rate limits, and invalid version
envelopes are not bypassed by retrying aliases. A legacy successful response that
does not satisfy contract v2 is reported as incompatible rather than accepted
under an unverified profile or resume context.

Errors show the backend HTTP status, API route, and safe backend reason/code.
A 'code generation failed; retry or ask an admin' response usually requires the
ApplyFlow administrator to inspect provider availability, model configuration,
credentials/permissions, quota, and the server-side generation logs. SQC cannot
repair backend AI credentials or determine the exact provider failure from that
generic message alone. Map provider errors separately from expired SQC user

SQC listens to browser tab URL updates as well as in-page history events.

An approved continuation in another tab may reuse only one unambiguous matching
session, including its reviewed local resume and audit screenshots.

Reject conflicting job identity or assignment claims; no route enumeration is required.

allowedRoutes may be omitted from context responses.

- Authenticate the applier and tenant, check active assignment ownership, and

Lease and synchronization behavior

SQC refreshes active content configuration every 30 seconds and caches successful
auth/context checks for at most 30 seconds. A content lease is capped at 60 seconds
and never outlives the server context or authentication expiry. Sign-out and
revocation therefore propagate within these polling/lease limits, not instantly.
Event delivery forces fresh authentication and context verification. If profile,
job, or resume versions changed since evidence was created, the event is rejected
until SQC refreshes. Different tabs maintain independent contexts. Verified data
is stored in trusted extension session storage, survives worker suspension, and
expires on browser-session termination. There is no offline identity fallback.

Long-running provider jobs: asynchronous backend response

Each SQC answer/status fetch has a 25-second deadline, with at most 120 seconds
total waiting. Return a completed batch promptly, or return HTTP 202 JSON:
{
  "success":true,"contractVersion":2,
  "applicationSessionId":"app_123","requestId":"batch_uuid",
  "jobId":"job_123","jobVersion":"3","profileId":"profile_123","profileVersion":"7",
  "resumeId":"resume_123","resumeVersion":"2",
  "status":"PENDING",
  "statusUrl":"/api/sqc/answer-questions/requests/batch_uuid"
}

SQC polls the supplied authenticated same-origin GET statusUrl every 3 seconds
(at most 40 polls, bounded by the total deadline). Every pending response must
echo the full identity/version envelope above. PENDING, QUEUED, and RUNNING are
recognized; subsequent responses can omit statusUrl to keep the previous URL.
The final response must contain the completed answers envelope. Reject redirects,
foreign origins, and cross-user status requests. Failed jobs can return status
FAILED with an error. Cancellation stops extension requests; it does not promise
to cancel a provider run already executing on the backend.

ApplyFlow owns the JHProIT integration: keep provider credentials server-side,
create chats, send grounded prompts plus output_schema, and poll provider runs
with a bounded timeout. Do not expose provider keys or send the extension to
provider URLs. This extension repository does not contain apps/api; provider
orchestration and the authenticated pending-status route require backend work.

Use future, server-generated expiresAt values in real contexts, actual file-byte
SHA-256 values (not an example or empty-file digest), and explicit verified
workAuth.authorizedInUS facts when available. Do not infer eligibility from an
unstructured workAuthType label. Record a final submission only after portal
confirmation and the event acknowledgement described above; an Apply navigation
button and a successful AI answer batch are not submission evidence.

Existing /api/ai/chat and /api/ai/status are not authentication or assignment
verification endpoints. AI availability alone must never unlock SQC.

Deployment policy and application continuity (main 1.3)

resume.mode is fixed or tailored. Fixed accepts an approved base resume without
per-job uploads, with an optional candidate-scoped replacement. Tailored scopes
uploads to the verified candidate/job/application. A backend job.tailoringRequired
true always requires tailoring. Uploads retain actual file format, use the locked
candidate's name as the attachment filename, and supply current document skills
and employment entries ordered current/newest to oldest. Rows are kept together;
ambiguous facts and unknown date precision are not invented.

Launch links should include application_session_id and optionally sqc_job_id and
sqc_profile_id. Ordinary ATS job_id query parameters are deliberately not treated
as ApplyFlow IDs. Browser onBeforeNavigate captures IDs before an HTTP redirect;
per-tab bindings and created-navigation-target events carry those discovery hints
through wrapper pages, ATS login, steps, SPAs and Apply-created child tabs. This
does not grant a lease. application-context must verify the original application
and verify the retained job/profile/session identity on each actual URL, including
login/wrapper steps. No predefined allowedRoutes list is required. Conflicting
job/profile identity pauses actions but keeps
the original tab association for later verification. Distinct launch sessions
remain isolated even when several jobs share an ATS domain or login page.

SQC_CAPTURE_STEP stores latest observed supported answers from each verified page
in session storage, scoped by auth/application/profile assignment/job. Password,
OTP, hidden and similar credential fields are excluded. At confirmed submission,
the existing webhook adds application_steps (url, label, fields, timestamps) and
screening_qa (question, answer, field_id, step, url, resume_id, resume_version).
The backend should retain this evidence alongside its existing audit payload.
An acknowledgement must echo accepted:true, eventId, applicationSessionId and a
nonempty recordId. Delivery acknowledgement alone is not a completed job status.
SQC refreshes application-context after delivery and while its sidebar is open;
the backend should return status SUBMITTED/APPLIED after persisting the record.
Until then the UI reports submission delivered with ApplyFlow status syncing.

LIVE PAGE COVERAGE (SQC 1.6.4)
The extension now reads committed values separately from unanswered AI inputs.
Filled fields from SQC autofill or manual entry contribute to Answered and Applied
without an AI request. Clearing a live field removes its filled status. These are
field-completion counts, not proof that the job application was submitted.
Each frame inventory is filtered through the same verified job scope as Q&A.
The Page field coverage list accounts for detected uploads and controls; details
report manual, unsupported and unlabeled controls. Conditional fields are scanned
when revealed; restricted frames/closed shadow roots may require manual handling.
No new ApplyFlow endpoint is required for the sidebar counts or image deduplication.

EXPLICIT FIELD ASSIGNMENT (SQC 1.6.5)
Candidate details and returned answers expose Assign to field. The extension
rescans the verified active job, lets the applier choose an unanswered field and
edit the value, then uses QA_APPLY_ANSWER with manual:true and the existing
document/context snapshot. It rejects changed assignments and edited fields.
It does not call the AI or require a new backend route to map these values.
Overview confirms the visible portal resume filename, including attachment rows
whose native file input has been removed by the ATS. Resume presence is distinct
from having a resume available in ApplyFlow or in the extension's context.
