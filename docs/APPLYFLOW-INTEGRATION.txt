ApplyFlow integration contract for SQC

Implement this contract in the ApplyFlow backend to enable the SQC authentication,
candidate profile, job context, and audit synchronization already implemented in
this repository. Contract version: 2. These new authentication/context routes are
requirements for the ApplyFlow agent; their existence is not assumed.

Scope

SQC now uses one user-selected ApplyFlow API origin. The user signs in with their
ApplyFlow applier email and password. The authenticated server session returns
the candidate profile assigned to that applier, which is locked across SQC job
tabs. Each job context must match this profile lock. Profiles are no longer seeded from JSON.
Candidate editing, local reassignment, admin passkeys, and extra webhook targets
are disabled. The existing ChatGPT copy/paste tools remain available only inside
a verified assignment. Screening requests are integrated with ApplyFlow; the
general chat UI is separate from application answering.

Authentication transport

The endpoint is the ONLY integration setting the installer/user supplies. Do not
ask the user to enter candidate IDs, applier IDs, API keys, extension IDs, AI
provider settings, or separate webhook URLs. The applier supplies their assigned
email and password in the dedicated SQC setup page. SQC sends
credentials to the configured ApplyFlow server and never stores them. ApplyFlow
owns account creation, credential verification, password policy, and assignments.
The extension opens its centered setup page on first installation, persists
the endpoint across browser restarts/extension updates, and uses the same flow
for an unpacked local installation and a Chrome Web Store installation.

1. The user enters the API origin in onboarding/onboarding.html and continues.
   HTTPS is required, except HTTP on localhost/127.0.0.1/[::1]. Paths, credentials,
   query strings, and hashes are rejected. Portal URLs cannot select API origins.
2. SQC checks GET /api/sqc/auth before accepting a new server, then requires
   explicit email/password sign-in through POST /api/sqc/login. It does not open
   a website login or adopt an existing website session during initial setup.
   ApplyFlow may be open in another Chrome profile or browser. No website login
   is required in the browser profile where the extension is installed.
3. All API calls originate in the service worker, use credentials: include,
   cache: no-store, and reject redirects. The login POST must establish the API
   session cookie in the extension's browser profile; subsequent API calls use
   that session. If ApplyFlow currently accepts only bearer tokens,
   add a supported cookie-based adapter for these routes before enabling SQC.
4. Permit the deployed chrome-extension://<extension-id> origin and the
   Content-Type, X-SQC-CSRF, and X-SQC-Extension-Id request headers. SQC supplies
   its actual chrome.runtime.id automatically on every request, for both unpacked
   and Store builds. Do not ask the user for this ID. Register permitted Store
   and development extension origins centrally on the backend. The extension ID
   is public client metadata, never proof of identity or assignment authorization.
   Configure credentialed responses
   for this origin explicitly; do not combine credentialed access with '*'.
   Test the actual Chrome cookie policy in the target deployment.
   In particular, test credential sign-in in a fresh browser profile with no
   ApplyFlow website cookies; a website session in another profile is irrelevant.
5. GET /api/sqc/session returns a session-bound CSRF token. The login POST uses
   the separate pre-authentication token from GET /api/sqc/auth. All POST requests
   include X-SQC-CSRF. Validate it, session access, and assignment ownership on
   the backend. No bearer token or CSRF token is exposed to portal content scripts.
6. 401 means signed out/expired; 403 means access denied/revoked. Never redirect
   API requests to login HTML. Return JSON errors for all other non-success cases:
   {"success":false,"error":{"code":"CONTEXT_MISMATCH","message":"..."}}

Extension setup and ready state

The setup page shows one step at a time: server, credentials, assigned profile
review, then the ready workspace. A temporary password must be changed before
profile review. Accounts without a candidate remain on an assignment waiting
screen with a retry action. Profiles are supplied by the server, never selected
or edited locally. Reviewing a profile records only a UI acknowledgement keyed
to the server, applier, assignment, and profile versions. It grants no permission
to autofill or submit; every portal still requires a backend-verified job context.

After setup, the toolbar popup shows the HUD-style workspace and waits for an
application. A verified active job tab shows its title and company. The portal
HUD sends unauthenticated users to the dedicated setup tab using OPEN_SETUP;
the service worker focuses an existing setup tab instead of opening duplicates.
Signing out returns to credential sign-in and clears the UI acknowledgement.

GET /api/sqc/session

Response (top-level shape, no data wrapper):
{
  "success": true,
  "contractVersion": 2,
  "session": {"id":"auth_123","expiresAt":"2030-01-01T13:00:00.000Z","passwordChangeRequired":false},
  "applier": {"id":"user_123","name":"Applier Name","email":"applier@example.com"},
  "csrfToken":"opaque_session_bound_csrf_value",
  "profileAssignment":{
    "id":"profile_assignment_123","version":"4","status":"ACTIVE",
    "applierId":"user_123","profileId":"profile_123","profileVersion":"7"
  },
  "profile":{
    "id":"profile_123","version":"7","verified":true,"fullName":"Candidate Name"
  }
}

Use the authenticated user, never a request applier ID. Session IDs must change
when the user signs out/signs in as another account. Applier identity is locked in
SQC. This endpoint must not return a list of unrelated candidate profiles.
Return the assigned profile even when no job tab is open, so the user can see
their locked assignment immediately after sign-in. Include the full verified
profile fields needed for display; the per-job context includes the approved
resume. Return profileAssignment:null and profile:null when no active assignment
exists; SQC then shows UNASSIGNED and blocks application actions. Do not silently
pick another candidate. Increment assignment.version on reassignment/revocation.

Applier credentials and password lifecycle

Provision the applier account and initial email/password in ApplyFlow using the
existing authorized administration flow. SQC does not create users or carry a
shared default password. A temporary password can be marked passwordChangeRequired
in the session; SQC blocks all job contexts until the password is changed.

GET /api/sqc/auth is available before login. It returns:
{
  "success":true,"contractVersion":2,
  "csrfToken":"opaque_pre_authentication_token",
  "expiresAt":"2030-01-01T12:05:00.000Z"
}
Bind this short-lived challenge to a pre-authentication HttpOnly cookie and
validate the actual permitted extension origin. It must not expose an applier
profile or create an authenticated user session. Return Cache-Control:no-store.

POST /api/sqc/login
Headers: Content-Type:application/json; X-SQC-CSRF:<pre-authentication token>
Body: {"email":"applier@example.com","password":"user_supplied_password"}
Response: {"success":true,"contractVersion":2}

Validate credentials with ApplyFlow's existing account system and establish a
rotated authenticated HttpOnly cookie. SQC then GETs /api/sqc/session, checks the
returned email matches the submitted email, and obtains the locked profile.
Invalid credentials return 401 with a generic error. Rate-limit login attempts.
Do not echo passwords into responses or logs, or accept applier/profile IDs as
credential substitutes. Passwords are cleared from the SQC form after submission
and from worker message objects after completion. No password is saved in Chrome
local/session storage or included in audit/event payloads.

POST /api/sqc/password
Headers: Content-Type:application/json; X-SQC-CSRF:<authenticated session token>
Body: {"currentPassword":"user_current_password","newPassword":"user_new_password"}
Response: {"success":true,"contractVersion":2}

Verify the current password, enforce the existing backend password policy, change
the password, and invalidate old authentication sessions. Rotate the current
cookie into a new session and clear passwordChangeRequired. SQC clears its old
context and fetches /api/sqc/session again. If the backend chooses not to preserve
the current session, return 401 on the next session check and require sign-in with
the new password. Wrong current password/policy failures return 400; missing or
expired authentication returns 401. Never change the assigned profile as a side
effect of a password change.

POST /api/sqc/logout
Headers: Content-Type:application/json; X-SQC-CSRF:<authenticated session token>
Body: {}
Response: {"success":true,"contractVersion":2}

Revoke the backend session and expire its cookie, including the corresponding
ApplyFlow browser session if they share it. SQC clears its cached identity and
records local sign-out even if the server is unavailable; automatic reconnect
must not silently reuse a leftover cookie. Sign-in explicitly clears this local
lock only after credential verification. Disconnecting the endpoint is separate
from signing out; use Sign out to revoke the authenticated session.

Launching an assignment

Create or reuse an authorized applicationSessionId for the tuple of tenant,
applier, candidate, and job. Launch the portal with this identifier in its hash:
https://boards.greenhouse.io/example/jobs/12345#application_session_id=app_123

Preserve any existing portal hash route and append parameters appropriately.
Explicit sqc_application_session_id in the query is also supported. Hash job_id
and profile_id, or query sqc_job_id and sqc_profile_id, are optional hints only.
SQC ignores ordinary ATS job_id query values as ApplyFlow IDs to avoid collisions.
Names, applier_id, server URLs, and stack labels in portal URLs are not authority.

POST /api/sqc/application-context

Headers: Content-Type: application/json; X-SQC-CSRF: <session token>
Request:
{
  "contractVersion":2,
  "applicationSessionId":"app_123",
  "url":"https://boards.greenhouse.io/example/jobs/12345#application_session_id=app_123",
  "jobId":"optional_explicit_applyflow_job_id",
  "profileId":"optional_explicit_applyflow_profile_id"
}

Optional identifiers are omitted when absent. A previously verified tab can
reuse applicationSessionId across authorized wizard/redirect routes. For a
standalone portal URL without a launch identifier, resolve only a single
unambiguous assignment that belongs to the authenticated applier. Return a
409 error if no unique assignment is available; never choose the first candidate.

Tailored resume uploads and source of truth

Each application uses either an uploaded tailored resume or an approved
ApplyFlow resume with kind:tailored and a matching jobId. Upload through
HUD > Resume > Upload tailored resume > Use tailored resume. The save button
confirms candidate/job ownership; there is no additional confirmation checkbox.
PDF, DOCX, and TXT files up to 10 MB are supported. SQC extracts readable text, displays experience
rows for review, and requires confirmation of the candidate/job. If extraction
fails, the applier can paste readable text alongside the original file.

ApplyFlow remains the source of truth for the base candidate profile: identity,
contact information, work authorization, sponsorship, location, compensation,
demographics, and other approved profile facts. Return these as structured,
versioned fields in session.profile and context.profile. A server-provided
verification prompt can accompany them as profile.verificationPrompt, but must
not be the sole representation of verification facts. SQC must not reconstruct
identity or legal eligibility from resume prose or from an AI answer.

The uploaded resume is a separate, applier-provided source for work-history
entries, descriptions, skills, and explicitly stated experience numbers. It
never updates the candidate's base profile. SQC labels it source:sqc_upload,
verified:false, and assigns resumeId 'sqc-upload:<file SHA-256>' and resumeVersion
'<file SHA-256>'. Those IDs are local document identifiers, not ApplyFlow resume
records. Original bytes are retained in extension-owned IndexedDB with a browser
session epoch and bounded retention, scoped to the authenticated account,
assignment/profile/job versions and application session. A local upload does
not depend on ApplyFlow's default resume ID/version; refreshing that default
does not discard the selected upload. A byte-matched downloaded ApplyFlow copy
is persisted with server provenance and is invalidated if its server version or
fingerprint changes. Logout clears the local documents. Assignment/job/version changes
invalidate them; the document must be uploaded for the new application context.

A valid job/profile assignment can return context.resume:null when no server
resume exists. This verifies the assignment, not a nonexistent resume. Basic
candidate details remain fillable, while resume-driven answering waits for an
upload. Existing approved server resume metadata/downloads remain supported for
viewing and attachment. A verified job-tailored server resume is ready without
re-upload. An unclassified/base document does not satisfy job tailoring.

Parsed employment rows retain exact source evidence, company, role, month/year
dates, current-employment status, and responsibilities. Supported existing
experience rows are filled in order. The extension does not create arbitrary
portal-specific rows or invent missing employers, dates, or durations. The user
must review parsed rows, add missing portal rows, and complete unsupported
controls. A month-only source never produces an invented day. Explicit numeric
experience facts include their source sentence; unknown skill durations are
left for review. Ambiguous dates and employment layouts remain unfilled.

Screening pipeline with a local resume

Once a tailored resume is active, SQC automatically batches detected unanswered
questions through
POST /api/sqc/answer-questions when candidate/custom-question autofill is enabled.
It applies returned answers to the original fields only if the assignment, job,
resume, field shape, and user-entered values still match. A manual Answer with
Codex control remains available for retry; Stop cancels automatic generation for
the current resume context. Needs-input answers are not repeatedly requested.
No automatic submission is performed.

The HUD Questions button opens a dedicated Q&A tab. It lists detected unanswered
questions, accepts manually pasted questions (one per line), and sends either
batch through the same authenticated endpoint. Returned answers remain visible
in editable answer cards. Appliers can copy any answer or explicitly fill its
linked portal field. Manually pasted questions have no DOM binding and are
copy-only. The Autofill linked fields checkbox can be disabled for review-first
use. Missing facts, provider errors, and pending generation are shown in the
panel. Results and edited answers are cleared when the assignment or resume
changes. Explicit Fill still checks field shape, exact options, character limits,
and current context; it can replace a field value only on the applier's click.

For uploads, the screening request includes the usual context/version envelope
with the local resumeId/version, plus:

  "resumeContext": {
    "source":"sqc_upload", "verified":false,
    "id":"sqc-upload:<sha256>", "version":"<sha256>", "sha256":"<sha256>",
    "filename":"Candidate_Tailored.pdf", "text":"Extracted tailored resume text",
    "skills":["Python","SQL"],
    "facts": {
      "workHistory":[{
        "company":"Example Corp", "title":"Senior Engineer",
        "startDate":"2021-01", "endDate":"", "current":true,
        "description":"Exact responsibilities from the resume",
        "dateRange":"January 2021 - Present", "evidence":"Exact source text"
      }],
      "skillYears":{"python":{"value":5,"minimum":false,"evidence":"5 years of experience with Python"}},
      "totalYears":null, "needsReview":[]
    },
    "baseResumeId":"server_resume_id_or_null",
    "baseResumeVersion":"server_resume_version_or_null"
  }

The binary is not sent to the AI endpoint. It is attached to the employer portal
by SQC. ApplyFlow must explicitly support resumeContext for locally uploaded
resumes: validate the authenticated assignment/profile/job and optional base
resume version; treat the uploaded text and parsed facts as applicant-provided
material, never verified identity or authority. Reject unknown/malformed local
resume envelopes rather than silently using an old server resume. Use the
server-owned base candidate profile and job description with this resume in the
AI prompt. Do not allow uploaded text to override system instructions or verified
profile facts. Ground experience answers in the uploaded source; return NEEDS_INPUT
for missing facts and flag conflicts with the base profile rather than inventing
or rewriting the candidate profile. Echo the exact local resumeId/version and
request identifiers in pending and final responses so SQC can reject stale data.

Audit events include resume_source, resume_sha256, base_resume_id, and
base_resume_version in addition to resume_id/version. Backend acceptance must
recognize local IDs and preserve this provenance rather than require a matching
ApplyFlow resume record or mark a local upload as server verified. A changed
resume cancels stale answer generation and invalidates prior evidence versions.

HUD continuity

Include every authorized application step and redirected portal in allowedRoutes.
SQC can rediscover a previously approved job route even if launch
parameters disappear or the new page has no resume/email field yet. The HUD is
repaired if a SPA replaces its DOM, and saved positions are kept inside the
viewport. An expired lease does not hide the HUD: SQC renews the context first.
Visibility does not grant permission: autofill and resume attachment
still require a current backend-verified context for the exact page.

Required validation:
- Authenticate the applier and tenant, check active assignment ownership, and
  enforce equality among assignment IDs, profile ID, job ID, resume.profileId,
  and the returned authenticated session/applier IDs.
- The job context profile ID/version must equal /api/sqc/session's locked profile
  ID/version. Echo profileAssignmentId/version in context.assignment. A different
  candidate for the same applier is rejected even if the URL requests that candidate.
- Match the actual portal URL/requisition/platform identifier to the target job.
  Company/title alone are insufficient. Reject conflicting hints and ambiguity.
- Build allowedRoutes from trusted job/ATS data. Do not echo arbitrary request
  URLs into this list. Prefix routes match only path segments. Include identifying
  query parameters when a platform uses them to distinguish jobs.
- Authorize each redirect, login, confirmation, and embedded application frame
  explicitly. Do not whitelist an entire shared ATS host or '/' for subpaths.
  Every frame verifies its own URL with the worker; page postMessage cannot
  install identity or profile context. Cross-frame AI injection is not implemented.
- Omit unknown optional profile facts; never supply invented defaults for
  authorization, sponsorship, salary, demographic answers, or experience.
- A server resume may be null. A non-null server resume must still have verified
  ownership and version metadata. The uploaded tailored resume supplies the active
  experience context. Never synthesize a substitute file or candidate identity.
- Existing profile sections such as eeoc, location, technicalExperience,
  backgroundAndEducation, and customFields can be supplied as verified objects.

Lease and synchronization behavior

SQC refreshes active content configuration every 30 seconds and caches successful
auth/context checks for at most 30 seconds. A content lease is capped at 60 seconds
and never outlives the server context or authentication expiry. Sign-out and
revocation therefore propagate within these polling/lease limits, not instantly.
Event delivery forces fresh authentication and context verification. If profile,
job, or resume versions changed since evidence was created, the event is rejected
until SQC refreshes. Different tabs maintain independent contexts. Verified data
is stored in trusted extension session storage, survives worker suspension, and
expires on browser-session termination. There is no offline identity fallback.

Submission and live-event synchronization

Keep these existing endpoints and add authenticated ownership/version checks:
POST /api/submissions/webhook
POST /api/submissions/live-event

Requests retain the existing SQC evidence/validation fields and add:
{
  "contractVersion":2,
  "event_id":"random_event_uuid",
  "application_session_id":"app_123",
  "job_id":"job_123","job_version":"3",
  "profile_id":"profile_123","candidate_id":"profile_123","profile_version":"7",
  "profile_assignment_id":"profile_assignment_123","profile_assignment_version":"4",
  "applier_id":"user_123","applier_name":"Applier Name","applier_email":"applier@example.com",
  "profile_name":"Candidate Name","profile_assigned":"Candidate Name",
  "resume_id":"resume_123","resume_version":"2",
  "is_final_submission":true,
  "submission_confirmed_by":"CONFIRMED_ON_PORTAL_SUCCESS_PAGE",
  "job_status":"SUBMITTED","validation_status":"PASSED",
  "extracted_data":{},"screening_qa":[],"screenshots":[],
  "timestamp":"2030-01-01T12:00:00.000Z"
}

Re-derive identity/ownership and the applier profile lock server-side, validate
profile assignment, profile, job, and resume versions, and deduplicate
event_id within the assignment. Reject stale versions with 409. Do not treat
PENDING/IN_PROGRESS, REJECTED, BLOCKED, or PORTAL_ACCESS_FAILED as a successful
application. Prevent downgrading an already submitted application. Screenshot
evidence can include a generated form summary when browser capture is unavailable;
it is not by itself proof that the portal accepted an application.

Both endpoints MUST respond with this acknowledgement shape:
{
  "success":true,"accepted":true,
  "eventId":"the_exact_request_event_id",
  "applicationSessionId":"app_123",
  "recordId":"stored_record_id"
}

SQC reports successful delivery only after this acknowledgement. Existing
responses containing only success:true are insufficient. Local audit history
stores acknowledged metadata; visual evidence is sent to ApplyFlow and retained
in bounded extension session storage. No automatic durable retry queue is part
of this phase. A failed or timed-out dispatch must be retried explicitly; the
backend must never infer that failed delivery means the portal application failed.

AI screening integration (implemented extension contract)

SQC calls POST /api/sqc/answer-questions with the authenticated session cookie
and X-SQC-CSRF. Keep /api/submissions/answer-questions and
/api/ai/answer-questions as backend aliases for existing clients; SQC uses the
canonical /api/sqc route. All responses must be JSON, never login redirects.

Request:
{
  "contractVersion":2,
  "applicationSessionId":"app_123","requestId":"batch_uuid",
  "jobId":"job_123","jobVersion":"3","profileId":"profile_123","profileVersion":"7",
  "resumeId":"resume_123","resumeVersion":"2",
  "url":"https://boards.greenhouse.io/example/jobs/12345",
  "questions":[
    {"id":"stable_field_uuid","question":"Why this role?","type":"textarea","required":true,"maxLength":1000},
    {"id":"stable_choice_uuid","question":"Years of Node.js experience?","type":"select","required":true,"options":["1-2 years","3-5 years","5+ years"]}
  ],
  "customInstructions":"Optional instructions, at most 4000 characters"
}

Resolve candidate/job and tenant from the authenticated assignment, rather than
arbitrary client names. Before model execution, validate active assignment,
job/profile/resume versions, correct tailored document when required, and the
exact authorized job route (employer hostname alone is insufficient). Repeat
authorization/version validation before releasing results, including polled
results. Use 403 ASSIGNMENT_REVOKED and 409 VERSION_MISMATCH for those failures.

Completed response:
{
  "success":true,"contractVersion":2,
  "applicationSessionId":"app_123","requestId":"batch_uuid",
  "jobId":"job_123","jobVersion":"3","profileId":"profile_123","profileVersion":"7",
  "resumeId":"resume_123","resumeVersion":"2",
  "answers":[
    {"id":"stable_field_uuid","status":"NEEDS_INPUT","answer":"","reasoning":"Candidate facts do not support a grounded answer."},
    {"id":"stable_choice_uuid","status":"ANSWERED","answer":"5+ years","matchedOption":"5+ years","confidence":0.98}
  ]
}

Echo contractVersion, requestId, and every application/job/profile/resume ID and
version exactly, even when strings look numeric. Answer IDs must be unique and
belong to the request. ANSWERED requires a nonempty string. For select/radio
questions, answer and matchedOption must equal a literal supplied option. Never
guess unknown employment, eligibility, clearance, demographic, or experience
facts: return NEEDS_INPUT. Honor maxLength; SQC leaves overlong answers for review
rather than silently truncating them. Supported types are text, textarea,
number, select, radio, and checkbox (checkbox choices are Yes/No).

The extension snapshots visible unanswered native controls and their stable
IDs before dispatch. It verifies context again before filling, preserves edited
or replaced fields, highlights completed fields green and NEEDS_INPUT fields
amber, and never submits or advances the application. Stop cancels local waiting
and filling; signing out, navigating, reassignment, or a version change invalidates
the result. This action does not use the legacy manual-paste fuzzy matcher.

Long-running provider jobs: asynchronous backend response

Each SQC answer/status fetch has a 25-second deadline, with at most 120 seconds
total waiting. Return a completed batch promptly, or return HTTP 202 JSON:
{
  "success":true,"contractVersion":2,
  "applicationSessionId":"app_123","requestId":"batch_uuid",
  "jobId":"job_123","jobVersion":"3","profileId":"profile_123","profileVersion":"7",
  "resumeId":"resume_123","resumeVersion":"2",
  "status":"PENDING",
  "statusUrl":"/api/sqc/answer-questions/requests/batch_uuid"
}

SQC polls the supplied authenticated same-origin GET statusUrl every 3 seconds
(at most 40 polls, bounded by the total deadline). Every pending response must
echo the full identity/version envelope above. PENDING, QUEUED, and RUNNING are
recognized; subsequent responses can omit statusUrl to keep the previous URL.
The final response must contain the completed answers envelope. Reject redirects,
foreign origins, and cross-user status requests. Failed jobs can return status
FAILED with an error. Cancellation stops extension requests; it does not promise
to cancel a provider run already executing on the backend.

ApplyFlow owns the JHProIT integration: keep provider credentials server-side,
create chats, send grounded prompts plus output_schema, and poll provider runs
with a bounded timeout. Do not expose provider keys or send the extension to
provider URLs. This extension repository does not contain apps/api; provider
orchestration and the authenticated pending-status route require backend work.

Use future, server-generated expiresAt values in real contexts, actual file-byte
SHA-256 values (not an example or empty-file digest), and explicit verified
workAuth.authorizedInUS facts when available. Do not infer eligibility from an
unstructured workAuthType label. Record a final submission only after portal
confirmation and the event acknowledgement described above; an Apply navigation
button and a successful AI answer batch are not submission evidence.

Existing /api/ai/chat and /api/ai/status are not authentication or assignment
verification endpoints. AI availability alone must never unlock SQC.

Acceptance checks for the ApplyFlow agent

Test email/password login, invalid credentials, temporary-password enforcement,
password changes and old-password rejection, logout with failed server delivery,
an authenticated applier with no assigned profile, expired login, wrong applier,
wrong tenant, reassignment,
candidate/profile/resume version updates, a resume belonging to another candidate,
ambiguous standalone jobs, different jobs in two tabs, route redirects, embedded
form URLs, and a logout during context retrieval. Verify that forged URL names,
applier IDs, API origins, and candidate IDs do not change identity. Test duplicate
event IDs, failed acknowledgements, and stale versions without marking jobs applied.

SQC local checks: npm.cmd test; npm.cmd run build on Windows (npm on other systems).
Load dist/extension as an unpacked Chrome extension. Connect to the implemented
API origin, sign in, refresh the popup, then open an assignment from ApplyFlow.
Live end-to-end acceptance requires these backend routes and a Chrome session.
